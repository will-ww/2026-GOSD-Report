# GOSD 2026 新材料深度研究与重构建议

研究评审稿 v0.1 · 2026年11月4日

本稿研究 GitHub Octoverse 2026、Hugging Face 春夏两轮观察及相关原始研究，判断它们会怎样影响《2026全球开源发展报告》的问题、证据和叙事。它是正式编写第一章前的研究输入，不是新的报告正文，也未替代已批准的报告宪法。文中“建议”“候选判断”均等待评审。

## 供评审的主要结论

**建议保留“参与、供给、复用、治理与公共价值”的全书主线，改变的是提问深度，而不是立即重排六章。** 新材料最有价值的启示不是“再加几组增长数字”，而是：当代码和模型供给快速增加时，必须追问谁把它们转化为可用、可信、能够持续维护的能力，以及这种转化对不同群体意味着什么。

建议采用以下总问题组织重构：

> AI 正在改变开放成果的生产与复用方式。供给增长之后，哪些参与者、技术条件和治理安排，使这些成果能够持续被使用，并形成可验证的公共价值？

这是一条研究问题，不是已证明的因果链。它对现有主张的影响有四点：

1. **参与要观察角色，而不只统计账号。** 人类开发者、自动化流程和 Agent 的工作交织，提交、审阅、批准与维护由谁承担，需要在指标中保留区别。
2. **供给增长与实际采用必须分开。** 仓库、模型、下载和派生关系分别提供不同信号，任何一种都不能独自证明使用质量、生产率或公共收益。
3. **中间参与者应进入叙事。** 项目维护者、模型适配者、量化与工具开发者、文档贡献者和部署机构，连接基础供给与实际使用。其作用需要对象、关系和案例证据，而不能仅由头部排行榜推断。
4. **治理是转化过程的一部分。** 开放许可、材料透明、审阅测试、依赖条件、部署责任与结果评价，分别影响成果是否可用以及谁能从中受益。

不建议据此写成“Agent 已普遍提高生产率”“开放模型数量证明公共价值增长”或“开放必然带来普惠”。本轮材料足以改进研究设计，尚不足以替代 GOSD 的主期实证。

## 一 研究范围与可比性

### 1.1 决策问题与材料选择

本次服务于两项决策：第一，哪些新事实和方法应进入报告；第二，哪些原有候选主张需要加强、收窄或暂缓。主要读者仍为政府和国际组织决策者，兼顾企业、基金会、研究者与社区。

核心材料由用户指定。补充资料按作用纳入：GitHub 的平台观测以 METR、DORA 和 AIDev 的原始研究补足任务与工作流层面的解释；Hugging Face 的平台观察与模型生态论文相互核对；开放定义与公共价值问题采用 OSI、DPGA、ITU 和独立 DPG 研究。厂商自报、研究实验、观察数据、规范文本和机构倡议不混为同一证据等级。

本轮完成原文与方法核查、来源关系去重及叙事影响分析；没有重算 GitHub 私有遥测、下载所有外部数据包、对全球 Agent 活动重新识别，或对公共服务项目做独立成效评价。相关缺口在后文列明。

### 1.2 三种时间位置必须并列保留

GOSD 主统计期保持 **2025年7月1日至2026年6月30日**，不因新材料更晚发布而改变。

### 1.3 来源之间不是等权且独立的多票表决

HF Summer 博客与其 GitHub Markdown 是同一来源的两个载体。Spring 博客与 Economies 研究存在作者和引用联系，不能简单写成两个独立团队相互验证。GitHub 年报及产品说明属于同一平台来源链；METR两篇属于同一研究系列；AIDev数据集与其子集分析共享底层样本。DORA还涉及平台合作关系。我们采用这些资料是因为它们回答不同问题，而不是用来源数量制造确定性。

## 二 开发协作材料改变了什么

### 2.1 从活动数量进入工作流

Octoverse 2026 的新增价值在于揭示 Agent 已进入代码生产与审阅流程，但其检测是可见信号的下限，平台默认范围也包含私有活动。没有 Agent 配置不能判定没有使用 AI，公开活动之外也不能凭现有数据还原全球开发实践。[GitHub Octoverse 2026，Glossary与Methodology](https://github.blog/news-insights/octoverse/octoverse-commits-pushes-reach-new-highs-in-2026-as-developers-build-with-agents/)

**对GOSD的建议：** 保留既定的人类参与主指标，在可验证条件下增加自动化与 Agent 补充视角。先做小样本标识审计，记录“可识别／未知”，再考虑扩展；不能直接把无法识别的事件全部算成人工或全部剔除。正文应解释计数对象，而非只把更大的事件量放在开篇。

### 2.2 更高产出不自动等于更高生产率

平台观察、随机任务实验和工作流访谈测量不同对象。METR早期研究针对熟悉开源项目的开发者和当时工具；2026年的设计更新又明确报告参与、任务选择及并行计时的问题。因此，不能只挑早期减速结论，也不能把后续弱信号写成普遍提速。DORA的限定组织研究则提示核验工作可能与生成便利同时增加。[METR早期研究](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)、[METR更新](https://metr.org/blog/2026-02-24-uplift-update/)、[DORA工作流分析](https://dora.dev/insights/balancing-ai-tensions/)

**对GOSD的建议：** 将“产生多少修改”“多少修改被接受”“接受后是否持续维护”分开。审核时间、返工、任务类别与后续质量应作为潜在研究字段，而不是立即承诺已有完整数据。这使第三章对关键主体的解释比排名更具体，也为第四章理解测试、运行和审阅工具的角色提供依据。

### 2.3 Agent研究不能跳过任务与样本

AIDev可提供公开PR互动与事件时间线的可复现研究入口，但其精细子集有仓库筛选条件，底层采样也不等于2026全平台。基于它的任务分析同样受任务分配和反馈筛选影响。本轮不采用其中存在表述冲突的具体工具排名，而保留按任务和项目条件分层的启示。[AIDev](https://arxiv.org/html/2602.09185v1)、[任务分层研究](https://arxiv.org/html/2602.08915v1)

**改变的是分析单位：** 从“哪个工具更强”转向“在什么任务、项目和审查条件下，何种工作被接受并持续使用”。这与报告的生态评价定位一致，不应把本报告改写成编码Agent产品评测。

## 三 模型生态材料改变了什么

### 3.1 从发布者数量进入可用供给链

HF春夏观察把基础模型以外的衍生、适配、量化、工具和子社区带入视野。对GOSD而言，最值得保留的不是单个家族的热度，而是观察对象的改变：基础能力生产者、再加工者、分发者和实际采用者并非同一种主体。相同仓库数可能对应不同形式的劳动，也可能包含镜像和重复格式。[HF Spring](https://huggingface.co/blog/huggingface/state-of-os-hf-spring-2026)、[HF模型卡字段](https://huggingface.co/docs/hub/model-cards)

建议第五章使用“基础模型—衍生类型—分发／适配主体—工具与部署条件”的关系记录。量化、微调、合并、格式转换和镜像分开，不统一叫作原创模型创新。多父模型、缺失谱系和平台外开发单列。跨GitHub/HF映射需要实体证据，仅在README里出现GitHub链接不足以证明相同项目或控制关系。[EMSE原始研究](https://livablesoftware.com/wp-content/uploads/2025/01/EMSE___HF_for_Empirical_Studies-3.pdf)

### 3.2 扩大参与与集中依赖可以同时存在

模型发布者增多并不排除基础家族集中。建议分别考察“谁发布或适配”与“依赖哪个基础家族”，不要把两种归因加总。向上递归归因可显示基础依赖，却可能抹去下游劳动；只按发布者计算则可能遮蔽上游集中。因此，集中度应成为多视角问题，不是寻找一个最大百分比作为中心结论。[Economies of Open Intelligence，归因与模型／开发者层分析](https://www.dataprovenance.org/economies-of-open-intelligence.pdf)

这不是已经在GOSD主期算出的发现，而是一项需要本期数据检验的假设。它适合连通第三章主体影响、第四章支撑技术和第五章模型复用，且不改变三章各自职责。

### 3.3 存量依赖和新品扩散需要不同观察尺度

下载计数受文件、库和请求方式影响，不能直接替代独立用户或生产部署。对新品，可以研究同龄、同任务或同规模条件下的扩散；对存量组件，则应观察持续依赖与维护状态。RAM提供同龄比较的参考设计，但其精选样本仍以HF下载为底层信号，不能消除平台覆盖偏差。[HF下载机制](https://huggingface.co/docs/hub/models-download-stats)、[Relative Adoption Metric](https://atomproject.ai/relative-adoption-metric)

社区讨论的短周期也不等于使用寿命短。独立FAccT研究观察到的模型社区活动与跨模型迁移，适合解释社群机制，不能改写成所有模型的生产生命周期。[The Brief and Wondrous Life of Open Models](https://facctconference.org/static/docs/facct2025-206archivalpdfs/facct2025-final2273-acmpaginated.pdf)

### 3.4 两项数字定义不一致与一项方法张力

|问题|核查发现|本轮处理|后续可执行验证|
|---|---|---|---|
|集中度样本定义|Spring将49.6%表述为前200模型，EOI方法则是265周各取Top200后的2,875模型并集|不把该数写成静态Top200集中度；保留文献表述差异|固定本报告主期，另算明确对象与窗口的CR10/100/200|
|老模型下载的含义|Summer将持续下载解释为基础依赖；EOI采用发布后一年过滤以降低陈旧自动化影响|不替作者裁定唯一解释，不把模型年龄直接等同无效下载|并列原始、可得去重、年龄过滤、任务／格式分层结果，辅以小样本流程检查|
|Agent份额及分母|Summer五月Claude Code约64%的表述与本次数据集6.405%不一致；数据覆盖带标记Agent流量，非全Hub用户总体|暂停相关排名与“Agent已是第一大用户”强结论；不自行认定笔误或回填原因|锁定数据与博客版本，核查归因变化、unknown类别和请求／用户分母|

直接依据：[HF Spring相关段落](https://huggingface.co/blog/huggingface/state-of-os-hf-spring-2026)、[EOI方法第2节](https://www.dataprovenance.org/economies-of-open-intelligence.pdf)、[HF Summer第5—6节及方法](https://huggingface.co/blog/state-of-open-models-summer-2026)、[官方Agent数据集](https://huggingface.co/datasets/huggingface/agent-usage)。前后两项属于待澄清的数字或定义不一致；中间一项是不同样本和目的下的解释与过滤策略张力，不是对同一现象的直接互相否定。这些差异不推翻整篇材料，也不允许忽略问题后摘录有利数字。

EOI的数据终止时间在摘要、正文和来源表中还有需要澄清的差别。本轮将它作为历史研究与方法来源，不用于主期趋势拼接。完整定位与敏感性方案见[HF专题研究](hf_research_review.md)。

## 四 开放条件怎样连接公共价值

### 4.1 技术可见性、使用权与修改能力分别记录

OSI 1.0提供开放AI的规范参照：除自由外，还涉及修改所需的数据说明、代码和参数。它不是现成的模型合格名单，也不能简化为训练数据原件是否全部公开。报告对具体对象应核对版本与材料，不能仅凭权重下载或许可证标签判定完整开放。[OSI定义](https://opensource.org/ai/open-source-ai-definition)

建议附录B采用多轴记录：权重可得性、使用／修改／再分发权利、运行与训练代码、数据信息、强制依赖、文档及评测。每格区分已核实、来源声明、未提供、未核实或不适用，不用一个“开放总分”掩盖不可比项。报告中的研究判断不等同法律意见或机构认证。

### 4.2 公共品登记不替代本地实施评价

DPGA标准审核核心方案，而非每个本地实施。2026年10月实践指南强调部署文档、依赖及SDG关联等可检查条件，可作为期后规范参照。独立DPG隐私研究则提醒，登记材料与细化实施保障之间仍有证据距离；其2023样本和威胁建模结果不能推广为2026所有项目的现状。[DPGA标准](https://www.digitalpublicgoods.net/standard)、[2026实践指南](https://content.digitalpublicgoods.net/A_Practical_Guide_to_the_DPG_Standard_0249fee444.pdf)、[SOUPS原始研究](https://arxiv.org/html/2406.15842v2)

**对报告的改变：** 公共价值不是前面榜单的自然终点。应逐步建立“问题—采用者—流程—可观察结果—限制”的案例证据。规范提供评价问题，案例提供实施过程，结果数据提供成效依据；三者不能互相替代。

### 4.3 公共服务案例以过程为主，不预先写成成功故事

ITU的GENIE.AI倡议可作为候选案例：它显示从框架、数据和原型到场景合作的组织过程。机构页面可以证明其自报活动和时间线，不能证明覆盖人口、节约成本或公平收益已实现。[ITU项目页](https://www.itu.int/en/ITU-D/ICT-Applications/Pages/Initiatives/ITU_OSPO/Open-Source_AI_for_Public_Services/About_the_Initiative.aspx)

第一章因此可以建立三个互补观察点：成熟软件如何共同维护，模型如何经适配成为可用供给，公共服务如何组织实施。这不是要求第一章塞入三个长案例，而是用少量证据揭示从发布到使用之间的工作。GENIE.AI是否进入正文，仍须评审其代表性和资料完整度。

## 五 对已批准主张的修订建议

以下是待评审的精炼方案，不自动改写宪法或替换现有C1—C6。六章、四视角、主统计期和第四／第五章分工均保留。

|主张|保留部分|建议加强或收窄|需要的新证据|当前状态|
|---|---|---|---|---|
|C1 开放协作与公共价值|公开发布不是价值形成的终点|加入人机供给扩张后的审核、适配与实施条件；避免自动因果链|共同维护、模型适配及公共服务过程案例|研究设计获得支持，净公共收益仍待验证|

## 七 第一章的具体编写建议

### 7.1 保留章节职责，重做引入逻辑

建议第一章仍为“从开放协作到公共价值”，不把它变成新报告的摘要合集。章节要让读者理解本书为什么这样观测，以及后面的四个研究视角共同回答什么。

**1.1 共同创新与公共价值。** 以可持续共同维护与下游再创造为两种基础机制，加入AI供给扩张的新问题：生成内容增多后，谁审阅、适配、部署和维护？Linux等历史累计案例应标背景时点；GitHub/HF较晚材料用期后观察框，而不是直接作为主期年度发现。最后提出公共价值转化所需的条件，而不先宣布成效。

**1.2 开源发展目标。** 将参与、供给、复用、治理、公共价值分别转成可回答的问题。规范性目标与可观察指标放在不同层，不用图形箭头暗示所有环节必然实现。OSDGs保持本报告研究框架的身份，不误称联合国认证体系。

**1.3 指标与观察方法。** 用一页清楚区分账号／事件／仓库／模型／关系／结果；再用来源时间地图说明主期、历史、期后。指标定义与观察边界是报告可信度的一部分，不是全部移到附录的技术细节。

### 7.2 建议优先制作的图，不是已完成的分析

1. **观测期与证据类型地图。** 将官方平台报告、原始实验、模型论文、规范与机构案例放到真实时间轴上，直接说明为何不能混算。
2. **从开放供给到可用能力的机制图。** 两条路径并列：软件共同维护、模型下游适配；在交汇处呈现审阅、工具、文档、许可与部署条件。边只表示机制假设，不标未经测量的因果强度。
3. **同一指标的不同解释示例。** 以下载为例，展示访问、格式获取、自动流程、实际推理采用等可能用途；用案例而非假定比例说明需要补什么证据。

这三图优先服务第一章；全量集中度、谱系网络和地区对比保留到实证章节，避免第一章提前消耗全书材料。

### 7.3 出版技术约束

用户已明确后续章节采用中文友好的LaTeX模板，并嵌入中文字体。正式第一章应先验证模板与字体嵌入、图题和参考文献样式，再迁入正文。此前ReportLab样稿仅保留为图文设计参考，不把它作为出版模板继续扩大。PDF仍不入仓库；可复用结构化正文、图表源、数据与引用在批准范围内维护。本研究阶段不编写第一章正式稿。
