# GitHub 与人机协作开发证据研究

研究日期：2026年11月4日。用途：GOSD 重构决策与第一章研究准备；不是已获批准的报告正文。本轮阅读了下列原始来源的正文及方法部分；没有重算 GitHub 平台遥测，也没有下载、独立清洗 AIDev 全量数据。GOSD 主统计期仍为2025年7月至2026年6月。

## 核心判断

**建议保留“参与、供给、复用、治理与公共价值”主线，但把“人机协作下，数量如何转化为可持续价值”明确为贯穿各章的研究问题。** 新材料的价值不只是补充更大的数字，而是迫使我们重审数量指标的解释边界：事件、提交、审阅、合并、采用和公共收益应分别观察。

**不建议把全书改写成“Agent带来开源全面繁荣”或“AI已经普遍提升生产率”。** 平台观测、限定任务实验、问卷与实际项目数据测量的是不同对象。它们不构成同一条可直接拼接的增长曲线，也不自动互相否定。

## 一 新材料能直接支持什么

### G01 GitHub Octoverse 2026

GitHub 自报：年度窗为2025年10月至2026年9月，默认含公私仓，往年数字依新口径重算。9月可检测Agent起草PR占比超过40%；新仓中有Agent配置者平均提交约为无配置者8倍。Agent信号是下限，无配置不等于未用AI。贡献人数及事件剔除可识别机器人；行业分类为抽样文本模型估计。[G01，Glossary、Methodology、Developers are reshaping their workflow]

**本研究解释：** 这些发现适合用作“期后工作流变化”的观察窗口，不能并入GOSD主期同比。尤其不能将8倍差异改写为Agent造成8倍生产率提升：项目类型、规模、创建时间、团队选择和自动化密度都可能参与解释。平台总活动也不能全称为开源活动。

### G02 METR 早期2025随机实验

2025年7月发布的研究，在16名熟悉大型开源项目的开发者、246项真实任务中，随机允许或禁止AI辅助；允许AI的任务平均耗时增加19%。研究者明确将其限定为当时工具和特定工作环境的结果。[G02，Methodology、Core Result]

**本研究解释：** 它是抵抗“采用即获益”叙事的有力方法示范，却不是2026年所有开发者的效率结论。实验样本偏成熟项目，不能与新建原型仓库直接比较。

### G03 METR 2026实验设计更新

2026年2月更新指出，后续研究受到参与者拒绝无AI工作、选择性提交任务、报酬变化和多Agent并行计时的干扰。旧样本与新招募样本的提速估计不确定区间均跨过零；研究者不认为当前中心估计能可靠代表真实效应。[G03，正文及Wider adoption章节]

**本研究解释：** “被AI改变的任务选择”本身成为研究对象。评价不应只问相同任务快了多少，还应问新增了哪些任务、谁承担了审阅、失败或返工如何计入。不能只引用G02的减速结果而隐藏G03更新，也不能把G03弱信号写成已证实显著提速。

### G04 DORA 的工作流程研究

2026年3月的DORA分析采用Google工程师在2025年第三季度提供的1,110份开放式问卷回应，发现生成便利与核验负担并存；作者提醒问题设计可能诱导受访者更多谈代码生成。[G04，Research methodology及Hidden taxes]

**本研究解释：** 这适合作为机制解释，不代表全球开发者抽样。DORA由Google Cloud运行，GitHub参与其2025报告合作，因此不得把它包装成完全脱离平台利益关系的独立审计。它与METR和AIDev的研究设计不同，适合三角验证而非平均数值。

### G05 AIDev 数据集

2026年2月公布的AIDev论文以2025年8月1日为数据截止，汇集五类Agent的PR；精细子集限于超过100星的仓库，包含审阅、提交和事件时间线，任务类别由模型标注。论文提供Hugging Face、Zenodo和GitHub入口。[G05，第1至3节]

**本研究解释：** 这是可复现研究的候选基础，不是全平台Agent渗透率的分母。发表在2026年不意味着采样覆盖2026年。适合用来验证人机互动的指标设计，若加入正式实证，必须另行核实检测规则、许可、缺失与采样偏差。

### G06 基于AIDev的任务分层研究

2026年2月论文从上述精细子集中筛选7,156个已关闭、MIT/Apache许可且收到非作者反馈的PR。结果显示任务类别与接受率显著相关，作者明确不作因果解释。[G06，第3至5节]

**本研究解释：** 合并率受任务分配与项目政策影响，不足以排列Agent的普适能力。该论文摘要与结果段对部分具体Agent优势类别的描述存在不一致，本轮不采用其工具排名；仅采用已核对的方法边界及“分任务比较”的启示。G05与G06共享数据，不算两份独立实证样本。

### G07 GitHub Agent应用卡

现行GitHub应用卡区分云端Agent、代码审阅等能力，强调审阅与测试、权限与环境约束，并说明工具可能漏报或误报问题。[G07，Overview、Limitations、Best practices]

**本研究解释：** 此来源可验证产品治理机制的设计，而不能证明机制已经消除风险。可用来说明治理不只是末端伦理声明，也嵌入权限、测试、审阅和合并流程。因页面为动态文档，仅作为截至研究日的机制案例。

## 三 应如何改变全书主张

以下均为本研究提出的修改建议，等待评审；不是已验证的GOSD统计发现。

### 1 参与不再只等于账号出现

保留地区和开发者规模观测，同时补充“谁负责定义问题、生成修改、审阅和批准”的角色区分。人的账号可能提交Agent产出，机器人账号也可能承担真实维护；简单删除全部自动化事件与简单全部纳入都会损失信息。

建议采用双视图：主指标维持既定的人类参与口径，另建可识别自动化与Agent互动的补充视图。未知来源单列，不将未检测到Agent标为纯人工。是否能实现要先审核现有事件字段和标识规则；目前不应承诺全量识别。

### 2 供给不再只等于新增仓库和提交

新增供给、被接受的变化和长期维护是三个问题。供给越大，越应追问其中多少被复用、持续维护或及时淘汰。报告不能用事件总量替代质量，也不应反过来认为高频自动化必然低价值。

可设置可测量的分层：新建仓库、持续活跃项目、经审阅合并的变化、后续维护状态。未有可靠数据的部分先作为研究缺口，不为视觉完整强行拼接。

### 3 复用要连接生成能力与共同资产

Agent的生成能力依赖工具、库、模型、文档与可执行环境。建议第四章从“哪些技术热门”进一步追问“哪些环节让其他开发者能够构建、运行与核验”；第五章关注模型派生与采用条件。两章仍各司其职，不把开源软件复用等同于模型下载。

### 4 治理应在章节中出现，而不只在第六章

把治理观察分散到每个证据单元：权限与许可证属于可用边界，审阅与测试属于接受条件，人员和资源安排属于持续维护。第六章再将这些发现转化为有证据支持的行动，而不是从概念直接跳到建议。

### 5 公共价值必须经由采用与结果建立

行业名称、公共仓库或政策口号都不能独立证明公共收益。公共价值案例需要“问题—采用者—工作流程—可观察结果—限制”的证据链。优先用少量可核验案例，不根据README分类直接算出教育、医疗或气候成效。

## 五 优先研究任务与停止条件

1. **优先完成方法对照，而非追加榜单。** 将本报告与G01按窗口、平台、公开性、对象、事件、机器人及地域字段逐项对照，能比较的才画对照图。
2. **抽取一个小而可审计的人机PR案例集。** 先验证字段可用性与误判率，再决定是否扩展。不要将未经抽样验证的Agent识别写成全书方法。
3. **建立“供给—接受—持续维护”证据卡。** 选成熟开源项目、新建应用项目和基础工具各一类，保持案例异质性。
4. **第一章先形成待验证问题，而不是强结论。** 研究成果足以改写提问方式，不足以证明所有地区或行业的净收益。
5. **明确停止条件。** 当关键定义可比性清楚、重要冲突已解释、剩余缺口已登记时进入章节写作；不等待一个无法获得的全球Agent总量。

## 六 建议提交用户评审的决定

- 是否将“人机协作下的供给扩张与价值转化”作为第一章的新问题，而保持原五段主线和六章结构？
- 是否在原人类参与指标之外增加自动化/Agent补充视角，前提是可识别性验证通过？
- 是否将工作流核验与维护能力纳入治理讨论，而不是将治理限于许可或规范？
- 是否明确把Octoverse 2026作为期后观察与方法对照，不改变已批准的主统计期？
